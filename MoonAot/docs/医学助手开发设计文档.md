# MoonAot 子功能「医学助手」开发设计文档

- 版本：v0.2（设计已实施，2026-11-05 完成 build + AOT 发布 + 端到端验证）
- 日期：2026-11-05
- 宿主工程：`MoonAot/`（.NET 10 / NativeAOT / WebView2 / 内嵌 HttpListener / Vue 3 前端）
- 目标：把《西氏内科学》上中下三册 + 后续新增医学书籍 + 临床 JSON 数据，做成一个**可全局秒级检索、可精确跳回原书位置、可双链/图谱/注释/分类/收藏/模板化、可快捷扩展**的本地知识库子功能。

## 0. 决策摘要（请重点审阅）

| # | 决策 | 建议 | 理由 / 证据 |
|---|---|---|---|
| D1 | 数据存哪 | **独立 `data/medical.db`**，不动主库 | 现有 `publish/data/moonaot.db` 已 120,815,616 B（约 115 MB）；医学索引还会再增 100–250 MB，混库会拖慢书架、锁竞争、备份困难 |
| D2 | 检索索引 | **SQLite FTS5 `trigram` + 内存短词层** | 已实测随项目发布的 `e_sqlite3.dll` = SQLite 3.53.4，`ENABLE_FTS5=1`，trigram 建表/BM25/snippet/短语/前缀全部可用；但**2 字中文词（如"心梗"）trigram 查不到**，必须补一层 |
| D3 | 跳回原书 | **自渲染「章节精读视图」为主**，readest 原生阅读器只作为「打开原书」 | 三册 EPUB 的目录锚点 **原样只有 7.6%–8.5% 可用**（生成器把带空格标点的标题写进 `src`，正文 id 是去标点 slug）；归一化后 **100% 可重建**。自渲染可完全控制段落定位与高亮，不依赖第三方 CFI 实现 |
| D4 | 结构化粒度 | 章节树（h1–h4）+ 800 字 chunk + 概念命中位置 | 三册共 6,232,221 文本字符、7,997 个带 id 标题、约 7,800 chunk；这个粒度同时满足「搜得快」「跳得准」「图谱有边」 |
| D5 | 扩展方式 | **数据源适配器 + schema 驱动卡片 + 菜单清单** | 新书拖入即索引；药品说明书、指南、检验、模板都只是不同 adapter/schema，不新增路由/表结构 |
| D6 | clinical 数据 | **快照复制进 `data/medical/sources/clinical/` + manifest 版本** | 源目录属于另一个程序的 Release 输出，随时会被覆盖；只读引用会导致数据漂移 |

## 1. 现状勘察（全部为本地实测，非推测）

### 1.1 MoonAot 现有架构

| 层 | 现状 | 可复用点 |
|---|---|---|
| 宿主 | `Program.cs` → `AppHost.Run` → `MoonServer.Start()`（127.0.0.1 随机端口）→ `ShelfWindow` | 启动链路无需改 |
| 窗口 | `ShelfWindow`（主窗，Vue 书架）、`ReaderWindow`（readest）、`MediaViewerWindow`、`BrowserWindow` | **医学助手复用 ShelfWindow，不新增原生窗口** |
| HTTP | `MoonServer.cs`（2302 行 partial class）：`/api/*`、`/tiny/api/*`、`/zimapi/*`、`/wiki/`、`/shelf/*`、`/book/{id}` Range | 新增 `/medapi/*` 一个分支即可，模式与 `/zimapi/` 完全一致 |

| ZIP/EPUB | `ZipLite`（只读中央目录）、`EpubRepairService`（container.xml 大小写修复）、`MetadataService`（读 OPF） | 医学导入直接复用 `ZipLite`，无需引入 Zip 新依赖 |
| 其他 | `Jobs`（后台任务+进度轮询）、`OpenCC.NET`（简繁）、`Log`、`FilePicker` | 导入进度、简繁归一直接复用 |
| 前端 | `frontend/src` Vue 3 + vue-router + naive-ui + lucide + Vite；`build.outDir = ../Assets/shelf`，`base=/shelf/` | 新增一个 view + 一条路由 + 一个侧栏项；`npm run build` 产出即被 `Assets/**` 复制进发布目录 |

侧栏菜单定义在 `frontend/src/components/AppSidebar.vue` 的 `items` 数组，路由在 `frontend/src/router.ts`（`/wiki`、`/search`、`/toolbox` 等 14 项），新增子功能只需各加一行。

阅读器打开路径：`host.openBook(bookId)` → `ShelfWindow.OnWebMessageReceived("openBook")` → `AppWindows.OpenReader` → `/reader.html?ids=<bookId>`；阅读进度/定位由 `/api/bookconfig` 的 `location`（readest BookConfig）持久化。**注意：`reader.html` 只用 `URLSearchParams` 取 `ids`，没有公开的 CFI/anchor 深链参数**。

### 1.4 三个决定方案的关键发现

1. **目录断链是可修复的，不是死局**。`toc.ncx` 里 `chap_002.xhtml#第十一篇 重症医学（负责人：詹庆元）`，而正文是 `<h2 id="第十一篇重症医学负责人詹庆元">`。把 label/anchor 做 NFKC + 去标点空白 + 小写归一后，上卷 2750/2750 全部映射到真实 `id`（2449 个 id 与标题文本归一后完全相等）。**这就是「跳到相关页面」的地基**。
2. **影像图解目录几乎为空**（仅 4 个 navPoint），但正文有 163 个带 id 的 h1–h4 与 1162 张图 → 必须按「标题 + 图片序号」自建章节树，不能依赖 NCX。
3. **SQLite 能力实测**（`publish/e_sqlite3.dll`，ctypes 直调）：

   | 项 | 结果 |
   |---|---|
   | 版本 / FTS5 / RTREE | 3.53.4 / 1 / 1 |
   | `json_extract` | 可用（3.38+ 内置，不依赖 `ENABLE_JSON1`） |
   | `CREATE VIRTUAL TABLE … tokenize='trigram'` | 成功 |
   | `"心肌梗死"`、`"急性心"`、`"阿莫西林"` | 命中 |
   | **`"心梗"`（2 字）** | **不命中（trigram 最少 3 字符）** |
   | `bm25()` / `snippet()` / `AND` / 前缀 | 全部可用 |

   结论：**≥3 字走 FTS5；1–2 字、拼音、缩写走内存实体层 + chunk 文本快照扫描**。

## 2. 目标与范围

### 2.1 用户要的能力 → 功能映射

| 需求 | 对应功能 |
|---|---|
| 三册结构化、全局检索快速定位 | 章节树 + chunk + FTS5 全文索引 + 分层检索 |
| 相关条目快速跳到相关页面 | 段落级深链（章节 + chunk + 词高亮）+ 概念卡「在书中出现 N 处」 |
| 知识库图谱、双链 | 概念/章节/笔记节点 + 自动共现边 + 手动 `[[双链]]` + 反链面板 + Canvas 力导向图 |
| 手动注释、分类、收藏 | Markdown 笔记（带原文引用）+ 树形标签 + 多对多收藏夹 |
| 快捷添加新书 | 拖入/文件选择 → 适配器自动解析 → 后台 job → 完成通知 |
| 药品说明书速查 | `DrugLeaflet` 适配器 + 药品卡片 schema，与 825 条 drug.json 合并去重 |
| 整合 clinical JSON | 概念导入器 + 8 类卡片渲染器 + 706 份病历模板内置 |
| 保存模板 | 三类模板：检索式模板 / 笔记·卡片模板 / 内置病历文书模板（可另存、导出、置顶） |
| 作为 MoonAot 子功能 | `/med` 路由 + 侧栏「医学助手」+ `/medapi/*`，复用现有窗口与 HTTP 服务 |

### 2.2 非目标（明确不做）

- 不改动 `books` / `notes` / `configs` 等现有表与书架行为；不动 readest 静态构建。
- 不做联网检索、不调用云端 LLM、不上传任何病历或书籍内容（全部本地离线）。
- 不做医学决策/诊断推理，只做检索与知识组织；UI 上标注「仅供学习参考，不作诊疗依据」。
- 不做 OCR 重识别（已有 OCR 文本层）；不改原 EPUB 文件（只读）。
- 不引入 EF/FreeSql/HtmlAgilityPack/Elastic 等新依赖；不引入新的前端图可视化库（自绘 Canvas）。

                                       │
┌──────────────────────────── Med/ 服务层（新目录） ──────────────────────────────────┐

**插件边界**：任何新数据源只要实现 `IMedSourceAdapter`，就自动获得「导入 → 建索引 → 概念对齐 → 检索 → 跳转 → 收藏」全套能力；任何新卡片类型只要注册一个 JSON schema，就自动获得渲染/编辑/模板能力。这是「添加新功能快捷」的落地方式，不是口号。

## 4. 数据模型（`data/medical.db`）

独立连接串（照 `Database.cs`）：WAL + `synchronous=NORMAL` + `cache_size=-32000` + `mmap_size=256MB`。启动时 `PRAGMA user_version` 做版本迁移。

| 表 | 用途 | 关键字段 |
|---|---|---|
| `med_books` | 已登记的书/文档源 | id, book_id(可空，关联主库), title, volume, type, path, sha1, mtime, status, indexed_at, doc_count, char_count, chapter_count, meta_json |
| `med_chapters` | **章节树 / 跳转锚点** | id, book_id, parent_id, level(h1–h4), spine_index, href, anchor(真实正文 id), title, title_norm, page_hint, ord, char_start, char_end, img_count |
| `med_chunks` | 段落级检索单元 | id, book_id, chapter_id, ord, text, text_norm, char_start, char_end, p_start, p_end, img_refs |
| `med_fts` | FTS5 虚表 | `fts5(text, book_id UNINDEXED, chapter_id UNINDEXED, chunk_id UNINDEXED, tokenize='trigram')` |
| `med_concepts` | clinical 8 类 + 自定义概念 | id, type, name, name_norm, pinyin, initials, category, keywords, aliases_json, data_json, source, source_version |
| `med_synonyms` | 同义词/缩写/中英对照 | term, canonical_id, kind（如 `WBC→白细胞计数`、`AMI→急性心肌梗死`） |
| `med_hits` | 概念↔chunk 命中（图谱的边来源） | concept_id, book_id, chapter_id, chunk_id, tf, positions_json |
| `med_links` | 双链 | id, src_type, src_id, dst_type, dst_id, kind(auto_cooccur / manual / wiki), weight, note, created_at |
| `med_notes` | 用户注释 | id, title, body_md, target_type, target_id, chapter_id, chunk_id, quote, color, created_at, updated_at |
| `med_tags` | 可自定义树形分类 | id, name, parent_id, color, ord, kind(category / favorite / smart) |
| `med_tagged` | 多对多打标/收藏 | tag_id, target_type, target_id, added_at, note |
| `med_templates` | 模板 | id, kind(card / note / query / doc), name, schema_json, content_json, pinned, builtin, created_at, updated_at |
| `med_saved_queries` | 保存的检索式 | id, name, dsl_json, pinned, last_used_at, hit_count |
| `med_import_jobs` | 导入任务 | 复用 `Services/Jobs.cs`（内存态），DB 只存每本书的索引结果与错误摘要 |

核心 DDL 片段：

```sql
CREATE VIRTUAL TABLE med_fts USING fts5(
  text, book_id UNINDEXED, chapter_id UNINDEXED, chunk_id UNINDEXED,
  tokenize='trigram');
CREATE INDEX ix_chunks_book ON med_chunks(book_id, chapter_id, ord);
CREATE INDEX ix_hits_concept ON med_hits(concept_id, book_id);
CREATE INDEX ix_links_dst ON med_links(dst_type, dst_id);
CREATE INDEX ix_tagged_target ON med_tagged(target_type, target_id);
CREATE INDEX ix_concepts_norm ON med_concepts(name_norm);
CREATE INDEX ix_concepts_init ON med_concepts(initials);
```

**规模估算（待实测校准）**：623 万字符 → 约 7,800 chunk；trigram posting 约 1,800 万条三元组（去重后远小于此），预计 `medical.db` 120–250 MB；`med_hits` 按「每 chunk 平均 3–8 个概念命中」约 3–6 万行。所有写入用一个批量事务，避免逐行提交。

## 5. 结构化与索引管线

导入由 `Jobs.Start("med-import", total)` 后台执行，前端轮询进度；支持暂停/取消/重试/增量。

| 步 | 处理 | 关键点 |
|---|---|---|
| 1 登记 | 计算 sha1 + mtime，写 `med_books(status=pending)` | 已存在且 hash 未变 → 跳过；源文件只读 |
| 2 解析包 | `ZipLite.Open` → `META-INF/container.xml` → OPF → `spine`/`manifest` | 复用 `MetadataService.ResolveOpfPath` 思路；不解压整包 |
| 3 **重建目录** | 读 `toc.ncx` / `nav.xhtml` 的 navPoint（含层级、playOrder、src），把 label 与 `src#anchor` 做 `NormalizeTitle`（NFKC → 去标点/空白 → 小写 → 简繁统一），映射到正文 `<h1..h4 id=...>` 的归一 id | **实测上卷 2750/2750 可映射**；映射失败降级为「同 chap 内标题文本模糊匹配 + 顺序对齐」，仍失败则记为无锚点章节（只到 chap 级）。影像图解 NCX 只有 4 项 → 走「扫描全部 h1–h4 生成章节树」分支 |
| 4 切分 | 以带 id 标题为 section 边界，`<p>` 为最小单元，聚合 ≤800 字 chunk（跨段不拆词），记录 `p_start/p_end`、`char_start/end`、`img_refs` | 保留「段落序号」而不是 CFI：OCR 书没有稳定页码，段落序号最稳 |
| 5 归一 | 全半角 NFKC、OpenCC 繁→简、去页眉页脚/重复标题/连续空白、数字单位标准化，生成 `text_norm` | 原文 `text` 永不改写，展示用原文、检索用归一文本 |
| 6 建索引 | 批量事务写 `med_chunks` + `med_fts`；同时把 chunk 纯文本载入内存快照（`MemoryMapped` 或 `string[]`，约 12 MB UTF-16） | 供 1–2 字短词扫描，实测 623 万字符全扫 < 100 ms 量级 |
| 7 概念对齐 | 用 `med_concepts`（2102 名称）+ `med_synonyms` + 拼音/首字母构建 Aho-Corasick 自动机，扫描每个 chunk，写 `med_hits`（tf + 位置） | 长词优先、避免嵌套重复命中；药品商品名/缩写单独走别名词典 |
| 8 自动双链 | 同 chunk 内共现概念对 → `med_links(kind=auto_cooccur, weight=共现次数)`；clinical `data` 中引用到的其他实体（如 disease.symptoms 中的症状名）→ 语义边 | 手动 `[[...]]` 与用户连线的 `kind=manual` 优先级更高、不可被自动重算覆盖 |

**导入完成报告（UI 显示，也是验收指标）**：章节数 / chunk 数 / 索引字符数 / 锚点重建率（目标 ≥99%）/ 概念命中数 / 断链修复数 / 耗时 / DB 增量。

**增量策略**：书级 hash 判定；单章重解析不影响其他书；concept 词典更新只重跑 step 7–8，不重跑 1–6。

## 6. 检索设计（分层，全部本地）

| 层 | 数据 | 命中方式 | 目标延迟 |
|---|---|---|---|
| L0 实体热层 | 2444 条 clinical + 用户收藏/模板/笔记标题（内存） | 名称前缀 trie、拼音、initials、别名，`Ctrl+K` 即输即出 | < 20 ms |
| L1 全文层 | `med_fts` trigram | 短语 `"…"` / `AND` / `OR` / 前缀，BM25 排序，`snippet()` 高亮 | < 150 ms（P95） |
| L2 短词层 | 内存 chunk 文本快照 | 1–2 字词、正则、OCR 容错（编辑距离 1），并行扫描 + 位置回放 | < 100 ms |
| L3 兜底 | `TinySearch`（现有全盘搜索） | 文件名级，找未登记的新资料 | 现有能力 |

**统一检索 DSL**（`POST /medapi/search` 或 `GET ?q=&...`）：

```json
{
  "q": "心肌梗死 阿司匹林",
  "mode": "phrase",              // exact | phrase | prefix | fuzzy | regex
  "scope": ["chunk","concept","note","template"],
  "types": ["disease","drug","guideline"],
  "books": ["<med_book_id>"],
  "tags": ["<tag_id>"],
  "pinyin": "auto",              // 纯拉丁输入自动按 pinyin/initials 匹配概念
  "sort": "relevance",           // relevance | book_order | recent
  "limit": 50, "offset": 0
}
```

**结果分组顺序**：① 概念卡（疾病/药品/检验/指南，带类型图标与摘要）→ ② 书内命中（书名·卷 → 篇 → 章节路径 + 高亮片段 + 「跳转」按钮）→ ③ 我的笔记/收藏/模板 → ④ 相关概念与反链入口。

排序权重：`概念名精确命中 × 章节标题命中 × BM25 × 概念权重(疾病/药品 > 通用词) × 收藏加权`；同书内可按 `spine_index, ord` 切回「按书顺序」浏览。

**拼音/首字母**：直接吃 clinical 现成的 `pinyin` / `initials` 字段（例：`fr` → 发热、`xlsj` → 心力衰竭、`amxljn` → 阿莫西林胶囊），书本内容则用 `med_synonyms` 的人工别名词典，不做全书拼音索引（体积不划算）。

## 7. 跳转与「章节精读视图」

深链格式（前端 hash 路由，可复制、可写进笔记）：

```
/med#/read?book=<med_book_id>&chapter=<chapter_id>&chunk=<chunk_id>&q=<urlencoded>
```

后端 `GET /medapi/chapter?id=&highlight=` 做三件事：
1. 从 EPUB 用 `ZipLite.ReadEntry` 取出对应 `chap_xxx.xhtml`；
2. 清洗：删除外部字体/脚本、把 `<img src="images/...">` 重写为 `/medapi/asset?book=<id>&path=<urlencoded>`（**按需流式读图，不落盘**），给每个 `<p>` 注入 `id="p{n}" data-chunk="<chunk_id>"`；
3. 返回 `{ html, chapterPath, prev, next, concepts, backlinks, images }`。

前端渲染后自动滚动到 `chunk`，对查询词/概念词做 `<mark>` 高亮（多色：查询词 / 疾病 / 药品 / 检验），右侧栏同步显示「本章概念、反链、我的笔记」。图片懒加载 + 点击放大。

**与原生阅读器的关系**：视图右上角提供「在静读阅读器中打开」→ `host.openBook(bookId)`，打开 readest 原书（到上次进度）。**MVP 不承诺 CFI 级跳转**，理由：`reader.html` 只解析 `ids`，没有公开 anchor 参数；往 `/api/bookconfig` 注入 `location` 需要验证 foliate-js 对自造 CFI 的容忍度，属于 P2 的独立验证项，验证通过再加「精确跳到原生阅读器」按钮。

**页码语义**：三册为 OCR 重排 EPUB，无印刷页码。UI 用「上卷 · 第 X 篇 · 章节名 · 段落 n」表达位置；`page_hint` 预留给从正文/图片序号推断出的原书页码，不保证准确，明确标注为「参考」。

## 8. 知识图谱与双链

**节点**：`concept`(8 类) / `chapter` / `chunk` / `note` / `tag` / `book` / `image`。
**边**：`auto_cooccur`（同段共现，带权重）、`semantic`（clinical data 字段引用，如疾病→症状/药品）、`manual`（用户连线）、`wiki`（笔记里的 `[[概念]]`）、`citation`（笔记→原文 chunk）。

**概念详情页**：头部是 schema 驱动卡片（按 type 选渲染器）；下方四个区：
- 「在书中出现」：按卷/章节聚合的命中列表，点击直达精读视图；
- 「相关内容」：按边权重排序的概念、指南、检验、药品；
- 「反链」：所有引用了本概念的笔记/模板/收藏；
- 「我的注释」：可新建、可 `[[双链]]` 到任意节点。

**图谱视图**：自绘 Canvas 2D 力导向（不引入新依赖），支持以任一概念为中心的 1/2 跳展开、类型筛选与颜色、节点点击直达、边权阈值滑杆、布局快照保存为模板。默认只渲染 ≤200 节点，避免卡顿。

## 9. 注释 · 分类 · 收藏 · 模板

| 能力 | 设计 |
|---|---|
| 注释 | 选中原文 → 右键/快捷键「添加注释」→ Markdown 笔记，自动带上 `book/chapter/chunk/quote` 引用；笔记内 `[[概念]]` 自动建 wiki 边与反链；支持颜色、置顶、全文可搜 |
| 分类 | `med_tags` 树形，自定义名称/颜色/父级；任意对象（章节、概念、笔记、图片、书籍、检索式）可打多标签；支持「智能分类」= 一个已保存的检索式 |
| 收藏 | 复用 `med_tagged`，内置 `★ 收藏` 特殊标签；`Ctrl+D` 收藏当前对象；收藏夹按标签树分组，可批量移动/导出 |

| 导入导出 | 模板/分类/笔记/收藏打包成单个 JSON（含版本号），可备份、迁移、分享；与 `medical.db` 的备份按钮分开 |

## 11. clinical JSON 整合

1. 首次启动把 8 个 JSON + `manifest.json` **复制**到 `data/medical/sources/clinical/2026.08.21/`，记录 `source_version`；外部源目录更新后，用户点「检查更新」才重新导入（可 diff）。
2. 每条记录 → `med_concepts` 一行：`data` 原样存 `data_json`（`json_extract` 已实测可用，必要时可查子字段），`pinyin`/`initials`/`keywords` 建索引，`category` 映射为默认标签树。
3. 8 个卡片渲染器：`disease / symptom / drug / lab / procedure / guideline / document / template`，字段布局由 schema 定义（见 1.3 表），用户可自定义字段显隐并另存模板。
4. 药品类 `data` 存在异构子类型（部分条目是相互作用/配伍/抗菌谱），渲染器按「存在哪些 key」动态选布局，不丢字段、不强行规整。
5. 概念与书的关联在导入管线 step 7 建立，所以搜「阿莫西林」会同时出现：药品卡、西氏内科学里的原文段落、相关指南、我的笔记——这是本功能的核心价值。

## 18. 附录：本轮实测依据

- EPUB 结构：Python `zipfile` 读取 `container.xml` / `content.opf` / `toc.ncx` / `EPUB/chap_*.xhtml`，统计字符、标题、图片、锚点命中（原始 src 与归一化后两套）。

### 19.3 实施中发现并修复的四个根因

1. **独立库初始化递归**：`MedDatabase.Open()` 在 `Initialized=false` 时回调 `Initialize()`，而 `Initialize()` 内部又调用 `Open()` → `/medapi/status` 直接超时。改为初始化时用原生连接，不走 `Open()`。
2. **.NET 正则命名组编号陷阱**：.NET 中命名组编号排在所有未命名组之后，`\1`/`\2` 反向引用会指向错误的组。NCX 目录解析因此只拿到 **233/2750** 项，报告却显示「233/233 = 100%」的假成功；OPF manifest 与章节图片重写也受同一问题影响。全部改为命名反向引用 `\k<q>`，并把 NCX 改为 `<text>` / `<content>` 按位置配对。修复后锚点 2750/2750、图片 404 消失。
3. **正文丢失 21%**：首版 `ParseBlocks` 只取 `<p>`/标题，约 44 万字符在 `<div>`/表格等容器里没进索引（上卷 166 万 vs 实际 213 万）。改为顺序扫描全部标签间的裸文本片段，修复后 212 万字符，与实测总量一致。
4. **影像图解只切出 6 章**：NCX 仅 4 项但正文有 164 个标题。加「目录项 < 正文标题数一半时按 h1–h4 重建」分支，修复后 164 章、1162 张图可按章节浏览。

另外补了「短词→规范术语」别名扩展（`心梗`→`急性心肌梗死`、`WBC`→`白细胞计数`），以及主书库联动：导入 EPUB 时自动登记到静读书架，「在静读阅读器中打开」可直接复用现有 `ReaderWindow`。

### 19.4 已知边界（未验证 / 未实现）

- **UI 渲染**：Vue 构建产物与静态资源已验证可访问，但**没有在 WebView2 里做截图级视觉验证**（本轮通过 HTTP API 完成端到端验证）。
- **原生阅读器精确跳页**仍按设计放在 P2 之后：`reader.html` 只解析 `ids`，没有公开 CFI/anchor 参数；当前「在静读中打开」是打开原书，章节级跳转由医学助手自己的精读视图承担。
- 自动双链按 `weight` 排序封顶 40,000 条；OCR 文本未做纠错，仅做 NFKC/繁转简/空白归一。
- 库里保留 1 条说明书示例「布洛芬缓释胶囊（示例）」用于演示速查，可手动删除；`drug.json` 的 825 条不受影响。
- `med_fts` 删除书籍后 DB 文件不会自动收缩（WAL/空闲页复用），必要时可 `VACUUM`。
